# 고퀄 모션그래픽을 다시 만드는 법

> 뮤비 2(`mv-remotion/`)를 만든 과정을 다음 작품에 그대로 쓸 수 있게 정리한 문서다.
> 대상: Claude Code(와 에이전트)로 Remotion 영상을 만드는 사람. 영상 문법은 `ART.md`, 강의 화면 리듬은 `VIDEO-PACING-GUIDELINES.md`.

## 0. 한 줄 요약

품질은 그리는 기술보다 **순서**에서 나온다.

```
재기 → 매체에 맞게 방향 정하기 → 기준 장면 하나를 끝까지 → 바이블·편집표 → 병렬 제작 → 숫자와 정지 화면으로 검수 → 마감 → 사람 눈으로 한 번 더
```

첫 뮤비가 아쉬웠던 이유는 이 중 앞의 세 단계가 없었기 때문이다. 바로 코드부터 짰고, "통과 기준"이 문장(남보라 밤·금빛)뿐이었다.

## 1. 이번에 든 시간과 비용

| 단계 | 걸린 시간(벽시계) | 한 일 |
| --- | --- | --- |
| 진단 | 15분 | 첫 뮤비의 색·밝기·컷 길이·움직임을 숫자로 잼 |
| 키트 + 기준 장면 | 1시간 30분 | 실루엣 뼈대, 깊이 층 카메라, 하늘·도시·나방, 전환, 0:44~0:55 일곱 컷 |
| 바이블·편집표 | 30분 | 컬러 스크립트 11단계, 규칙 9개, 67컷 표 |
| 병렬 제작 | 약 1시간 | 에이전트 5개가 60컷(막별) |
| 통합·검수·렌더 | 약 1시간 30분 | 절반 크기 전체 렌더 12분, 1080p 48분(4코어) |
| 다듬기 | 약 1시간 | 사람이 본 뒤 약한 컷을 에이전트 3개가 고침 |

에이전트 토큰은 제작 라운드에서 약 210만 개였다. 이 비용의 대부분은 "읽기"(바이블·기준 장면·키트)다. 그래서 바이블과 기준 장면을 잘 써 두면 에이전트가 덜 헤맨다.

## 2. 단계별 방법과 요청 문장

각 단계에서 Claude에게 그대로 붙여 넣을 수 있는 요청을 함께 적는다.

### 2-1. 재기 — 감 대신 숫자

`mv-remotion/tools/measure.py`가 색(hue)·밝기(p5/p50/p95)·컷 수와 길이·움직임 완급을 잰다. 전후 두 편을 같이 넣으면 비교한다.

```bash
python3 mv-remotion/tools/measure.py 예전.mp4 새것.mp4 --every 15
```

| 지표 | 첫 뮤비 | 뮤비 2 | 기준 |
| --- | --- | --- | --- |
| hue 30° 칸 | 1칸(235~245°) | 8칸 | 감정이 바뀌는 수만큼 |
| 밝기 중앙값 | 10~21 | 구간마다 15~110 | 30 아래가 길면 프로젝터에서 뭉개진다 |
| 0:44~0:55 안의 컷 | 4개인데 1개만 검출(화면이 거의 안 바뀜) | 7개 | 컷이 숫자로 보여야 눈에도 보인다 |
| 움직임 p90/p50 | 2.1배 | 4.6배 | 클수록 완급이 있다 |

> 요청 예: "이 영상을 `tools/measure.py`로 재고, 정지 화면도 몇 장 뽑아서, 다른 사람들 작품보다 무엇이 부족한지 숫자와 근거로 말해줘."

### 2-2. 방향 — 매체가 잘하는 것에 이야기를 맞춘다

| 코드(Remotion·SVG)가 잘하는 것 | 못하는 것 |
| --- | --- |
| 입자(수백 마리 나방), 빛·번짐, 색 그라데이션, 카메라(시차·심도·흔들림), 박자 맞춤, 반복 가능한 수정 | 손그림 연기의 미묘함, 사실적 질감(천·피부), 복잡한 3D 모델 |

그래서 인물은 **실루엣**(포즈만 읽히면 된다)으로 두고, 감정은 **빛·색·카메라·입자**가 맡게 했다. 이야기는 그대로 두고 그리는 법만 바꿨다.

> 요청 예: "이 이야기를 코드로 만들 때 코드가 약한 부분(연기·질감)을 피하고 강한 부분(빛·입자·카메라)으로 감정을 옮기는 화풍을 두세 가지 제안해 줘. 각 방향의 장단점과 추천을 같이."

### 2-3. 기준 장면 — 가장 어려운 10초를 먼저 끝까지

전체를 얕게 만들지 말고, **가장 어렵고 가장 문제였던 10초**를 완성도 100%로 먼저 만든다. 이번에는 첫 뮤비에서 "같은 와이드 4컷"이던 0:44~0:55를 일곱 컷으로 다시 짰다.

- 컷마다 거리·각도가 다르다: 어깨 너머 → 인서트(한 박) → 옆 트래킹 → 올려다보기 → 익스트림 와이드 → 미디엄 → 3/4 클로즈업
- 큰 동작이 박에 떨어진다: 손가락이 달을 집는 순간이 박 64, 엉덩방아의 충격이 박 72
- 이 장면이 이후 모든 작업의 "통과 기준"이 된다. 에이전트에게 문장보다 이 파일 하나가 더 정확하다.

> 요청 예: "본편을 만들기 전에 0:44~0:55만 기준 장면으로 만들어 줘. 컷마다 거리·각도를 바꾸고, 예비동작과 박에 맞춘 충격을 넣고, 정지 화면과 저해상도 영상으로 직접 확인한 뒤 보여줘."

### 2-4. 바이블과 편집표 — 에이전트가 읽을 단 하나의 문서

`mv-remotion/ART.md`가 예시다. 들어가야 할 것:

1. **왜**: 예전 것의 약점 표(규칙이 어디서 나왔는지 알면 에이전트가 규칙의 취지대로 판단한다)
2. **규칙**: 명암, 실루엣, 얼굴은 빛이 있을 때만, 빛의 의미(차가움=기계, 금빛=사람), 글자 없음, 이징, 카메라, 박자, 매치컷
3. **키트 사용법**: import 한 줄과 핵심 API 몇 줄. 기준 장면 파일을 "먼저 읽어라"
4. **편집표**: `id · 시작→끝 · 색 키 · 들어오는 전환 · 화면 설명` 한 줄씩. 앞뒤 컷의 상태(이음새)가 표에서 보이게
5. **확인 방법과 예산**: 명령어, 검수 질문, 프레임 비용 한도

> 요청 예: "기준 장면을 바탕으로 아트 바이블과 전체 편집표를 `ART.md`로 써 줘. 컷마다 시작·끝 시각은 곡 분석의 박 번호로, 색 키와 전환을 적고, 앞뒤 컷의 상태가 이어지게."

### 2-5. 병렬 제작 — 브리핑 여섯 가지

막(구간)마다 에이전트 하나. 브리핑에는 꼭 이 여섯 가지가 있어야 한다.

1. **목표**: 무엇을 왜(사용자가 원하는 수준)
2. **읽을 것과 순서**: 바이블 → 기준 장면 → 키트
3. **고쳐도 되는 파일 / 안 되는 파일**: 자기 막 파일과 `actN-*.tsx` 보조 파일만. 공용 키트는 고치지 말고 막 파일 안에서 우회하고, 버그는 보고만
4. **이음새**: 앞 컷이 끝나는 상태, 다음 컷이 시작하는 상태, 거울·북엔드 컷(1번 도시 ↔ 65번 도시)
5. **확인 방법**: 막 하나만 묶는 진입점(`src/entries/actN.ts`)으로 정지 화면·저해상도 영상. 기계를 같이 쓰니 렌더 크기 제한
6. **보고 형식**: 만든 컷 한 줄씩, 시트 경로, 키트 문제와 우회, 가장 약한 컷

> 요청 예: "편집표의 1·2b·3·4·5막을 에이전트 다섯에게 나눠 맡겨 줘. 각자 자기 막 파일만 고치고, 막 진입점으로 검수하고, 두 번 이상 체크리스트로 스스로 고친 뒤 보고하게. 너는 보고가 올 때마다 시트를 보고 통과 여부를 판단해."

### 2-6. 검수 — 세 가지 눈

| 눈 | 도구 | 무엇을 보나 |
| --- | --- | --- |
| 정지 화면 시트 | `tools/stills.mjs --sheet` | 구도, 명암, 실루엣이 읽히는지 |
| 움직임 시트 | 저해상도 렌더 → 초당 5장 → `tools/sheet.py` | 멈춘 구간, 너무 이른 퇴장, 튀는 자세 |
| 숫자 | `tools/measure.py` | 색·밝기·컷·완급이 의도대로인지 |

컷마다 묻는 다섯 가지(ART.md §5): 검게 칠해도 동작이 읽히나 / 가장 밝은 곳이 시선이 갈 곳인가 / 앞 컷과 거리·각도가 다른가 / 큰 동작이 박에 떨어지나 / 직선 등속 움직임이 남았나.

이번에 움직임 시트로만 잡힌 것: 도약 컷 후반 0.8초가 멈춰 보임, 정점 컷에서 아이가 너무 일찍 화면 밖으로 떨어져 0.6초가 빈 화면, 폰 컷의 아이가 화면 아래에 너무 작게. 정지 화면으로는 셋 다 멀쩡해 보였다.

### 2-7. 마감 — 공통 개선은 키트에서 한 번에

여러 에이전트가 같은 약점을 보고하면 그건 키트 문제다. 이번에는 "클로즈업 얼굴이 가면 같다"는 보고가 세 번 와서 뼈대에 후드 그늘을 넣었고, 모든 클로즈업이 한 번에 나아졌다. 필름 입자·비네트도 컷마다가 아니라 `MV.tsx`에서 공통으로 건다.

### 2-8. 사람 눈으로 한 번 더

전체를 보고 "약한 컷"을 짚는 사람의 한 바퀴가 가장 값지다. 짚은 컷만 좁은 범위로 에이전트에게 다시 맡긴다(무엇이 왜 약한지, 어떻게 바꿀지, 확인할 시각까지 적어서).

> 요청 예: "전체를 봤는데 새벽 방, 실에 끌려 오르는 장면, 창문 비행, 폭풍 구름이 약해. 컷별로 원인과 고칠 방향을 정리해서 그 컷만 다시 다듬어 줘."

## 3. 이번에 실제로 밟은 함정

| 함정 | 증상 | 처방 |
| --- | --- | --- |
| 컷(함수)을 Remotion props로 넘김 | `s.render is not a function` | props는 직렬화된다. 컷 목록은 컴포넌트에 묶는다(`Root.tsx`) |
| GL 백엔드 | `swangle` 프레임당 4초 | 렌더 전에 백엔드별로 24프레임씩 재 본다. 이 컨테이너는 `swiftshader` 0.55초 |
| 박 번호 변환 | `B(n) = beat(2 + 4n)`이라 같은 박을 두 번 적은 길이 0 컷 5개 | 편집표를 코드로 검증한다(컷 목록을 뽑아 길이 0·음수 검사) |
| 작업 중 공용 키트 수정 | 다른 에이전트의 번들이 잠깐 깨짐 | 병렬 제작 중에는 키트의 API를 고정하고, 고칠 땐 내부만·즉시 타입 검사 |
| 막 하나만 미리보기 | 마지막 컷의 `c.dur`이 곡 끝(180초)까지 늘어남 | 컷 길이에 의존하는 애니메이션은 끝 시각을 명시 |
| 반투명 원 겹치기 | 구름·달에 거품 무늬 | 그룹에 불투명도를 주거나, 원 대신 윤곽 하나(`storm.tsx`) |
| 하늘 층 심도 흐림 | 별이 뭉개지고 렌더가 느림 | 무한 깊이 층은 `blur={0}` |
| 원본 용량 | 1080p CRF 18 = 450MB, GitHub 100MB 한도 | 원본은 커밋하지 않고, 전달용으로 다시 인코딩(1080p 110MB, 720p 26MB) |

## 4. 다음 작품을 시작하는 법

`mv-remotion/`을 복사해서 시작하면 된다. 새로 만드는 것은 세 가지뿐이다.

| 그대로 쓰는 것 | 바꾸는 것 |
| --- | --- |
| `src/lib`(카메라·하늘·도시·나방·폭풍·마감), `src/kid`(실루엣 뼈대), `src/MV.tsx`(전환), `tools/`(렌더·정지 화면·계측) | `src/lib/palette.ts`(컬러 스크립트), 곡과 박 분석(`../mv/tools/analyze.py`로 JSON), `src/shots/*`(컷) |

순서: 곡 분석 → 이야기 표 → 컬러 스크립트 → 기준 장면 10초 → 바이블·편집표 → 병렬 제작 → 검수 → 마감 → 사람 눈.

## 5. 더 올리려면 — 지금의 천장

- **연기**: 실루엣은 포즈까지만 전한다. 표정 연기가 필요하면 손그림 키포즈나 생성 이미지를 재료로 받아 코드가 움직이게(카메라·빛·입자) 하는 편이 낫다.
- **소리**: 지금은 곡만 있다. 나방 날갯짓, 착지, 번개 같은 효과음을 박에 맞춰 얹으면 체감 품질이 크게 오른다.
- **질감**: 종이·필름 질감 텍스처 한 장(이미지)을 층마다 옅게 얹으면 "벡터 그림" 느낌이 줄어든다.
- **사람 검수 횟수**: 이번에는 한 바퀴였다. 두 바퀴째부터는 컷 단위가 아니라 프레임 단위 지적이 나온다.
